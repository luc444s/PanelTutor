b42b4d4377a55240341ed80cc079fcd4cb6baeda | 2026-09-26T18:38:47-05:00 | Systutor Dev | perf(mail): reuse the SSH session and widen the accounts cache
Measured against the real provider: a cold read was 1240-1560 ms, and 560 ms of
that was an SSH handshake that bought nothing. The provider opened a session
per call, so every read, every mailbox creation and every password change paid
for one.

build_ssh_command() now builds the argv as a pure function, which is what makes
the transport testable without a connection. When MAIL_SSH_CONTROL_PATH is set
it adds ControlMaster=auto, so calls after the first reuse the session: steady
state drops to ~610 ms, and the end-to-end cold read from ~1250 to ~750 ms.
Empty keeps the argv byte-for-byte what it always was.

The socket directory is created and chmod'ed to 0700 every time. This is the
security part: a world-writable directory would let another local user
pre-create the socket and hijack the session, speaking to the mail server with
our credentials. If the directory cannot be created the provider logs a warning
and falls back to one connection per call, so the optimization can never break
startup. That fallback is not theoretical, it is what happened on the first run
here: /tmp exists on Termux but belongs to Android and is not writable by the
app.

The accounts cache goes from 60 s to 300 s, which is deliberately wider than
the frontend staleTime. A.SPEC 0001 aligned the two so the client would not ask
while the server could still answer from its own cache, and that was right then,
when both expired into a trip to the mail server. With Redis in between, letting
them drift is what avoids the trip: the client refetches every 60 s and gets a
0.4 ms Redis hit. Writes from the app still invalidate immediately, so the
wider TTL only bounds how long a mailbox added outside the app stays invisible.

18 new tests in test_provider.py cover the argv, the 0700 mode, the graceful
degradation and that the password never reaches the argv.
